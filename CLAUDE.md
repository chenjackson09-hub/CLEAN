# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # Start dev server (polling flags are set for WSL file-watching)
npm run build      # Production build (also type-checks and lints)
npm run lint       # ESLint via next lint
npm test           # Jest unit/component tests (jsdom)
npm run test:watch # Jest in watch mode
npm run regeocode  # Re-geocode cleaners that have an address (supports --dry-run)
```

**Do not run `npm run build` while `npm run dev` is running** — both write to `.next/`, and the production build will clobber the dev server's compiled assets (the page then renders unstyled). Stop dev first, or build in a separate checkout.

### Tests

Colocated `*.test.tsx` / `*.test.ts` run under Jest + Testing Library (jsdom). `jest.setup.ts` polyfills React Server Component / form APIs that the jsdom runtime lacks (`cache`, `useFormState`, `useFormStatus`) and provides a default `next/navigation` mock.

Many existing suites predate the current implementation (they target removed mock-data stores, older routes, and pre-refactor markup) and currently fail — they need updating to the current components. Add/refresh a colocated test when you change a component's behavior.

## Architecture

**Clean** is a cleaning-services marketplace: customers browse and book verified cleaners; cleaners manage availability and respond to requests; admins approve cleaner applications.

Stack: Next.js 14 App Router · TypeScript · Supabase (Postgres + Auth + Storage + Realtime) · Tailwind CSS · Resend (email).

### Route groups

```
app/
├── (auth)/       # /login  /register  /register/cleaner  /register/customer
├── (cleaner)/    # /cleaner/dashboard  /profile  /availability  /requests  /preview  /pending  /customers/[id]
├── (customer)/   # /browse  /cleaners/[id]  /bookings  /profile  /home
├── admin/        # /admin/dashboard  /applications  /cleaners  /customers  /bookings  /support  /blocked  /inactive  /availability
└── api/auth/signout/
```

Each route group has a co-located layout that renders its own nav: `(cleaner)/layout.tsx` → `NavLinks.tsx`, `(customer)/layout.tsx` → `CustomerNav.tsx`, `admin/layout.tsx` → `admin/Nav.tsx`. The cleaner and customer navs share the same responsive shape — icon-over-label on mobile, icon-beside-label on `lg` — and put the language toggle and sign-out inside a **Settings gear dropdown** (the cleaner nav's dropdown also shows the cleaner's name + status badge). Keep those two visually in sync when changing one.

- **The admin nav is a fixed shell (top bar + sidebar), not inline-per-page.** `app/admin/layout.tsx` is a Server Component wrapping every `/admin/*` route — it fetches the current user's `profiles` row (name + role), redirects non-admins as a defense-in-depth check alongside middleware's role gate, and renders `<Nav currentUserName={...} />` once plus `{children}`. Individual `admin/*/page.tsx` files no longer render `<Nav />` or a `min-h-screen` wrapper themselves — they just return their `px-6 py-6` content div directly; the layout owns the shared chrome so navigating between admin pages doesn't remount the nav (unlike before). `app/admin/loading.tsx` provides the Suspense fallback shown in the content area while a page's data fetches, so the nav never flickers.
  - `Nav.tsx` renders two pieces: a full-width `fixed top-0` **top bar** (all breakpoints) — "Admin" + the logged-in user's name on the start side, a settings gear on the end side (placeholder for a future profile picture) opening a dropdown with the language toggle + sign-out, plus a hamburger button (mobile only) opening a dropdown of the nav links — and a `fixed` **sidebar** (`hidden md:flex`, positioned below the top bar, `start-0`) holding just the nav links for desktop. Since the top bar is `fixed`, every admin page needs `pt-14` (handled once, in the layout's `<main>`); the sidebar similarly needs `md:ps-56` reserved on both the layout wrapper and the top bar/sidebar's own positioning. Mobile keeps a compact top bar + hamburger dropdown instead of a full sidebar.

**Page padding lives on each route group's layout `<main>`:** customer = `px-3 … sm:px-8`, cleaner = `p-3 pt-16` (small mobile padding — was `p-8`, see below). A few pages still pull a small **negative horizontal margin** on the page root that resets at `sm:` — e.g. `-mx-2 sm:mx-auto` on `/cleaner/requests` and `/cleaner/profile`, and `-mx-1.5 sm:mx-auto` on `/home`. `/cleaner/customers/[id]` is now just **centered** (`max-w-2xl mx-auto`, no negative margin). **The cleaner layout was reduced from `p-8` to `p-3`**, so any breakout margin sized for the old 2rem padding had to shrink: `(customer)/cleaners/[id]/CleanerProfile.tsx` (reused by the cleaner preview) full-bleeds with **`-mx-3 sm:-mx-8`** (matching the customer layout's `px-3 sm:px-8`, and the cleaner layout's `p-3`) — a flat `-mx-8` over-pulled ~1.25rem past each edge on mobile and caused horizontal scroll in both the customer profile and the preview. When changing any of these, match the negative margin to the **current** layout padding (mobile 0.75rem), not the old 2rem.

- **Admin "Availability" nav button is temporarily hidden.** The `/admin/availability` page still exists and is reachable by URL, but its entry in `admin/Nav.tsx`'s `NAV_ITEMS` is commented out because we're not yet sure admins need it. Uncomment that entry to restore the button (the `adminNav.availability` translations are already in place).

After login, `signIn` redirects by role via `ROLE_HOME` in `lib/roleHome.ts` (customer → `/browse`, cleaner → `/cleaner/dashboard`, admin → `/admin/dashboard`).

### Admin panel rebuild (in progress)

The admin panel is being rebuilt screen-by-screen against a stakeholder spec describing 6 target screens (Dashboard, Applications, Cleaners, Hosts, Requests, Matching Queue). Only **Dashboard** (`/admin/dashboard`) is built so far — it's the new admin landing page, with schema-backed KPI cards (no fabricated metrics). The remaining screens, sequencing, and the open product decisions behind them (e.g. why `cleaners.status` uses the values below) are tracked outside the repo in the planning doc from that work; `docs/chen-notes.md` tracks the broader, non-admin backlog of stakeholder feedback this rebuild is part of.

- **The dashboard header is a live greeting, not a static title.** `DashboardGreeting.tsx` is a client component that renders nothing until mounted, then computes "Good morning/afternoon/evening, {first name}" + the date (`weekday, day month`) from the *viewer's own local clock* (never the server's) — this sidesteps any server/client timezone mismatch, at the cost of a one-frame flash on first paint. Below that is a static `Region: {value}` line (`admin.dashboard.regionLabel`/`regionValue` — currently a fixed "Hula Valley", not computed from data; change the translation strings if the business's region changes or this needs to become dynamic later).
- **"Disputes Open" is real data, not fabricated: it's the count of unresolved `support_messages`** (`resolved = false`). It appears three places, all independently queried (no shared fetch — each is its own cheap `count`-only query): the Dashboard KPI card (→ `/admin/support`), a `NeedsAttentionPanel` entry when > 0, and a red `NavBadge` count next to **Support** in the sidebar. The same badge pattern shows on **Matches** using `unmatchedCount`-equivalent logic (pending bookings stale > 2h) — both counts are fetched once in `admin/layout.tsx` via the service-role client and passed into `Nav` as props, so they're live on every admin navigation.
- **The dashboard now surfaces real rating averages** (the `ratings` table exists). A combined **Ratings** KPI card ("Average platform rating") shows **The App** / Cleaners / Customers, each a **rating_count-weighted** mean of the denormalized `cleaners.rating_avg`/`customers.rating_avg` (a true mean of all ratings, not an average of averages; `rating_avg` is coerced with `Number()` since PostgREST returns `numeric` as a string) — the whole card links to `/admin/ratings`. That page repeats the same three averages plus a **Recent ratings** list (rater → ratee, score, date) pulled directly from the `ratings` table — real individual rating rows, not aggregated. It deliberately does **not** claim to show written feedback: ratings are numeric-only (1–5), there's no review-text feature, and the page says so.
- **"Top areas this week" is already fully automatic** (`TopAreasWidget.tsx`) — no manual place-name entry needed or possible. It buckets each booking's free-text `address` by its last comma-separated segment (a rough heuristic, documented in the component itself), so label quality depends on how customers write their address, not on any admin input.
- The **Recent activity** card (`RecentActivityFeed.tsx`) has **Last day / week / month** range pills, groups events by day (Today/Yesterday/date headers), and shows a colored dot per booking status + the time — fed the last ~31 days of bookings from `page.tsx`. It sits on the **left** of the two-column bottom grid (in LTR); `NeedsAttentionPanel` + `TopAreasWidget` are stacked together on the **right** — plain CSS Grid with no `dir`-conditional code, since the browser already mirrors column order for `dir="rtl"`.

### Admin list pages — shared table + support-style layouts

There are two visual patterns across the admin list screens; **keep new admin screens on one of them** rather than inventing a third.

- **Shared "table of rows" (`app/admin/adminTable.tsx`)** backs **applications, bookings, cleaners, customers, and blocked**. It's the single source of that look — edit it to restyle all five at once. Exports: `AdminTable` (title + count pill + optional `toolbar` + a CSS-grid header row + horizontal-scroll shell), `AdminRow` (one grid row; renders `cells[]`, an always-visible `actions` cell, and — when `expanded` is passed — a chevron that toggles an inline panel below the row), plus shared cells/badges (`NameCell` with gradient avatar, `ContactCell`, `TextCell`, `ServiceBadge`, `StatusPill`, `StatusFilterDropdown`, `NotesPanel`) and button class strings (`btnPrimary/btnBlue/btnGhost/btnDanger`). **Header columns and the row `template` must have the same number of grid tracks** (the trailing actions/chevron cell is the last track), so each list defines one `TEMPLATE` string and passes it to both `AdminTable` and every `AdminRow`. `StatusPill` maps application statuses (pending/needs_info/approved/rejected), booking statuses (accepted/completed/declined/cancelled), **and** the active/inactive/blocked filter (below) — extend that map for any new status. Each list is a thin `*List.tsx` client component that owns state + server-action handlers and maps rows to a per-entity `*Row` component holding that row's notes state; the older per-card components (`ApplicationCard`, `BookingReviewCard`, `CleanerListCard`, `CustomerListCard`) are now **unused** but kept so their colocated tests still pass.

- **Cleaners/Customers/Admins each have an Active / Inactive / Blocked / All filter** (`StatusFilterDropdown` in the table's `toolbar`, defaulting to Active) instead of separate Blocked/Inactive nav entries — see `lib/adminUserStatus.ts` for the shared `classifyUserStatus()`/`isInactiveSince()` logic (30-day-no-login cutoff, matching `/admin/inactive`'s own rule but applied consistently across all three roles rather than customers' extra "no requests" bucket). The three roles compute "blocked" differently because of how deletion works for each: **cleaners** are soft-suspended (`cleaners.status === 'suspended'` *is* blocked, checked directly, no DB scan needed), **customers** are hard-deleted so a blocked customer has no live row at all — the Customers page merges in `blocked_users` (role=`customer`) rows as read-only "phantom" entries (synthetic `blocked-{id}` id, no Delete action, no notes panel) alongside the real ones, and **admins** have no blocked state at all (deleting one deletes the account outright) — the Admins filter is Active/Inactive/All only, no Blocked option. `/admin/blocked` and `/admin/inactive` still exist and work standalone (same "hidden but reachable" pattern as `/admin/availability`), just no longer linked from the nav.
- **Support-style tabbed card list** backs **support** (`SupportList.tsx`) and **inactive** (`InactiveList.tsx`): a centered `max-w-3xl` column, a title, pill tabs (active = teal `#75C9C8`), and a vertical `<ul>` of `rounded-2xl` white cards. Use this for report-style screens that don't need aligned columns.

- **Palette (stakeholder-provided):** teal `#75C9C8` (primary/active), blue `#80A1D4`, lilac `#C0B9DD`, pale `#DED9E2`, cream `#F7F4EA`, plus gray/black/white. Page backgrounds are a flat `bg-[#EFEFEF]` (set once on `admin/layout.tsx`'s wrapper). Every admin list page is just a `px-6 py-6` wrapper around its `*List` — the `bg` + `<Nav />` live in the shared layout, not per-page.

- **The admin `Nav` collapses below `md`.** `admin/Nav.tsx`'s `NAV_ITEMS` render as the fixed sidebar at `md+`; below `md` (where the sidebar doesn't fit) the sidebar is hidden and the top bar's hamburger button opens a dropdown listing the same items. Both read from the one `NAV_ITEMS` array, so a new nav entry appears in both automatically. Adding a screen = add a `NAV_ITEMS` entry + an `adminNav.*` string (EN **and** HE).

- **Blocked users** (`/admin/blocked`, table `blocked_users`, migration `0017_blocked_users.sql`): deleting a cleaner/customer or rejecting an application snapshots the person's name/email/phone onto this list via `recordBlockedUser()` in `app/admin/actions.ts` (best-effort — wrapped so a failure never blocks the delete/reject; upserts on `email` to de-dupe). For **customers** the snapshot must happen **before** the hard-delete wipes the profile + auth row; cleaner delete is a soft `status='suspended'`. `unblockUser()` removes an entry. RLS-on, no policies → only the service-role admin client reads/writes it; the page degrades to an empty list if the migration hasn't been run yet. **This is record-only — it does not yet block re-registration** (open follow-up).

- **Inactive users** (`/admin/inactive`): computed on the fly (no table) from auth `last_sign_in_at`/`created_at` + `bookings.created_at`. Two buckets over a 30-day cutoff — **no login** (any non-admin user; falls back to account age so brand-new users aren't flagged) and **no requests** (customers only, since they're who send booking requests; falls back to account age). The **All** tab merges both, deduped by id, showing every reason's date line.

### Admin Applications & Cleaners lists — row actions, and linking to the real public profile

- **Clicking a cleaner's name/avatar in either the Applications or Cleaners list opens `/cleaners/{id}` — the exact same public profile page a customer sees** (`(customer)/cleaners/[id]/CleanerProfile.tsx`), not an admin-styled lookalike. There was briefly a separate `/admin/cleaners/[id]` mimic page (avatar/rating/stats card styled like the real profile); it was removed once the requirement became "show admins what customers actually see" instead of a re-implementation, and its admin-only actions (approve/reject, notes, badge) were folded into each row's own expand panel (below) so nothing was lost.
  - **This required two role-gate carve-outs**, since `/cleaners` is normally a customer-only path: `middleware.ts` has an `ADMIN_READABLE_CUSTOMER_PATHS = ['/cleaners']` list — inside the existing `CUSTOMER_PATHS` check, `role !== 'customer'` no longer force-redirects when the path matches this list **and** `role === 'admin'`. Every other customer path (`/browse`, `/bookings`, `/home`, `/profile`) stays customer-only. `app/(customer)/layout.tsx`'s own defense-in-depth redirect (mirroring `admin/layout.tsx`'s pattern) had to relax the same way: `role !== "customer" && role !== "admin"` instead of just `!== "customer"`. The layout still renders the full customer chrome (`CustomerNav`, `HelpWidget`) around the page for an admin visitor — deliberately, since "what customers see" includes that chrome — the only change is that admins aren't bounced before reaching it. No other customer page is reachable this way; an admin hitting `/browse` etc. directly still gets redirected home by middleware before the layout ever runs.
- **Both rows now show a compact icon stack instead of a wide "Message" text button** (`ContactIconStack` in `adminTable.tsx`, shared by both lists) — a chat-bubble icon on top (opens a small "coming soon" popover — no chat feature yet, same as before, just icon-triggered instead of a button+note that pushed the row taller) and a real `mailto:` envelope icon underneath (the email address is already on hand, no reason to fake it). This — plus shrinking the actions column now that it no longer needs to fit a full-width button — is what let both `TEMPLATE`s and `minWidth`s shrink enough that the tables fit most admin viewports without the horizontal scroll ("swipe") that was needed before. The Cleaners list's Delete button became an icon (trash glyph, same red-tinted style, same confirm-dialog behavior) for the same reason — the row previously needed `ContactIconStack` *and* a full-width Delete button side by side.
- **Approve/Needs Info/Reject, the admin-notes `NotesPanel`, and the ID-document link all live in each row's own expand panel** (the chevron `AdminRow` already renders next to `actions` when an `expanded` node is passed) rather than a separate page — one click on the row, no navigation, no scrolling. `ApplicationRow`'s expand panel shows a **Badge** row first (`admin.cleaners.badgeLabel` / a teal "New" pill via `admin.cleaners.badgeNew` when `cleans_completed < 5`, else `—`), then Approve/Needs Info/Reject (only while `status` is `pending`/`needs_info`), then the notes panel + ID-document link. `CleanerRow`'s expand panel shows the same Badge row, then just the notes panel (cleaners have no pending review). `ApplicationsList`'s parent component owns a `handleUpdateStatus(id, cleanerId, next)` that calls `updateApplicationStatus` and optimistically patches the row's `status`/`reviewed_at` in local state (so the tab counts and the Approved column update immediately, matching the existing `handleSaveNotes` pattern) — this replaced the standalone detail page's own status-handling.
  - **`cleans_completed` had to be added to `CleanerApplicationResult`** (`lib/types/application.ts`) and selected in `app/admin/applications/page.tsx`'s `cleaners` query — it wasn't previously read there, only on the `cleaners` table query for the Cleaners list.
  - `cleaners.status` can be `suspended` (the fourth canonical value, see the Types section) — `STATUS_PILL` in `adminTable.tsx` and the `admin.applications.status` translation map both gained a `suspended` entry to cover it (still used for the Cleaners list's `StatusPill`, which shows the Active/Inactive/Blocked `userStatus`, not the raw `cleaners.status` — but the raw value is used elsewhere internally and needed a label/style so it never renders a raw enum string).
- **Applications list (`ApplicationsList.tsx`) columns are Name / Contact / Rate / Location / Submitted / Approved / Status / (chat, email)** — Location is real data (`cleaners.address`), Approved shows `reviewed_at` (blank until approved). Since the Customer approval section below unified this list to also show pending customer signups, the row type is `UnifiedApplication` (`lib/types/application.ts`) rather than the cleaner-only `CleanerApplicationResult` it used to be — `lib/mockData/applications.ts` and the colocated `ApplicationCard.test.tsx`/`mockApplicationsStore.test.ts` still use `CleanerApplicationResult` (they test the old, now-unused `ApplicationCard`/`mockApplicationsStore`, kept only so their tests pass) and are unaffected by the type split.
- **Cleaners list (`CleanersList.tsx`) columns are Name / Status / Contact / Location / Rate / Rating / (chat, email, delete)** — the name subtitle is `admin.cleaners.joined` ("Joined: {date}", from the cleaner's latest `cleaner_applications.reviewed_at`, fetched alongside the cleaner rows in `app/admin/cleaners/page.tsx`).
- **A cleaner isn't tallied as a cleaner anywhere in the admin panel until their application is approved.** `app/admin/cleaners/page.tsx` queries `cleaners` with `.in('status', ['approved', 'suspended'])` (pending/rejected applicants never appear here — they only ever show on Applications). The dashboard's Cleaners KPI (`app/admin/dashboard/page.tsx`) follows the same rule: `totalCleaners` counts only `approved`+`suspended` rows. Since suspended cleaners still count toward the total (they were real, approved cleaners, just currently blocked), the KPI sub-text is **"`{active} active · {blocked} blocked`"** (`admin.dashboard.cleanersSub`, both EN/HE) — a true breakdown of the total. **Customers now have the same rule** (see the Customer approval section below) — the Hosts KPI counts only `status = 'approved'` customers too.
- **The "All Applications" sidebar entry shows a red count badge for pending applications, combining pending cleaner applications and pending customer signups** — the same `NavBadge` pattern already used for Support (open disputes) and Bookings/Matches (stale unmatched requests). `admin/layout.tsx` fetches `cleaner_applications`-pending and `customers`-pending counts in parallel and sums them (`pendingApplicationsCount`) so the badge always matches what the unified Applications list shows. This is what makes a still-pending application/signup "look unseen" in the sidebar until an admin acts on it.

### Customer approval

- **Customers now need admin approval before they can browse cleaners or book, mirroring how a cleaner isn't bookable until approved** (migration `0023_customer_approval.sql`: `customers.status` — `pending | approved | rejected`, default `'pending'` — plus `customers.status_reviewed_at`). **Every customer that existed before this migration ran was grandfathered in as `'approved'`** so nobody already using the app got locked out; only customers created after the migration starts out `pending`. There's no `customer_applications` table — a customer's own `customers` row *is* the review record (unlike cleaners, which have a separate `cleaner_applications` table plus `cleaners.status`).
- **A pending (or rejected) customer can still sign in and look around the rest of the app** (home, profile, bookings) — **the gate is specifically on browsing cleaners and booking**, not the whole account. `(customer)/browse/page.tsx` queries `customers.status` **in its own isolated query**, separate from the existing `address/lat/lng` fetch, and shows `WaitlistNotice.tsx` (the "Cindy" waitlist message, see below) instead of the search UI when `status` is positively `pending` or `rejected` — it never runs the cleaner-matching queries in that case. `createBooking` (`(customer)/actions.ts`) enforces the same rule server-side as the authoritative check, since a pending customer could otherwise still reach a booking form via a hand-crafted `/cleaners/[id]?date=...` URL without ever visiting `/browse`.
  - **Every one of these checks fails OPEN, not closed.** They only block when `status` is *positively* read as `'pending'`/`'rejected'` — a query error (migration not yet run, stale PostgREST schema cache), a missing row, or `status` coming back `null`/`undefined` all fall through to normal, unblocked behavior. This is deliberate: `/browse` and `createBooking` are the core of the product for every existing customer, so an infra hiccup on this one new column must never silently break browsing or booking for people it was never meant to affect. The admin-side queries (Applications, Customers list, dashboard KPIs, sidebar badge) are comparatively low-stakes (visible only to the admin, self-correcting the moment the migration runs) and don't carry the same fail-open treatment — see the migration-application note below.
- **The waitlist message is the same "Cindy" assistant persona introduced in the cleaner-side welcome bubble** (see the cleaner onboarding section above) — now established as a recurring cross-role character, not a one-off. `WaitlistNotice.tsx` (`(customer)/browse/`) renders the exact copy provided, split across several `browse.waitlist*` translation keys (EN/HE) so the "you're on the waitlist!" and closing line can render `<strong>`-bolded — there's no markdown parsing, just JSX composition around the translated fragments. Unlike the cleaner welcome bubble (a one-time dismissible popup gated by a `?welcome=1` query flag), this is **not** dismissible and **not** one-time — it's simply what `/browse` renders every time a still-pending customer visits, for as long as they remain pending.
- **The admin "All Applications" list is unified across categories** — `app/admin/applications/page.tsx` now queries both `cleaner_applications` (as before) and every row of `customers` (all statuses, so Approved/Rejected tabs still show customers too, not just pending ones), normalizes both into one `UnifiedApplication[]` (`lib/types/application.ts`) tagged `category: 'cleaner' | 'customer'`, and sorts the merged list by raw submission timestamp (kept as a `sortKey` through the mapping, stripped before the array reaches the component — the display `submitted_at` is already a locale-formatted string, which sorts wrong lexicographically). A customer's "Submitted" date is their `auth.users.created_at` (no separate application-submission timestamp exists for them). The category shows as a small pill in the `NameCell` subtitle slot (`admin.applications.category.cleaner/customer`) rather than its own grid column, so the table width is unaffected by mixing categories. Cleaner-only bits (the public-profile link, the Badge/"New" stat, the Needs Info action, the ID-document link) are conditionally rendered per row; a customer row's name is plain text, not a link (customers have no admin-facing profile page to link to). Approve/Reject write straight to `customers.status`/`status_reviewed_at` via new `updateCustomerApprovalStatus`/`updateCustomerNotes` actions (`app/admin/actions.ts`) — mirroring `updateApplicationStatus`/`updateApplicationNotes` but with no "needs info" state and no `blocked_users`/email-notification side effects (a rejected customer's account still exists and can be reconsidered later; there's no cleaner-application-style one-shot rejection flow for them yet).
- **The Customers list (`/admin/customers`) now excludes pending/rejected customers**, matching the cleaner list's `.in('status', ['approved', 'suspended'])` pattern — `app/admin/customers/page.tsx` adds `.eq('status', 'approved')` to its query. A pending/rejected customer only ever shows on Applications until approved.
- **Migration-application note:** unlike the availability-note column (a single non-critical action that just errors until its migration runs), `customers.status` touches the customer-facing `/browse` page and the `createBooking` action directly — **run `0023_customer_approval.sql` immediately after deploying this**, not "whenever convenient." Until it's run, the fail-open behavior above means the approval gate silently does nothing (every customer behaves as approved) rather than breaking anything — safe, but also means the feature isn't actually live yet.

### Availability & booking

- Cleaners set availability **per specific date** in `cleaner_availability` (the calendar at `/cleaner/availability`, 15-minute granularity). The older recurring `cleaner_weekly_availability` table still exists and is honored as a fallback, but its dedicated weekly-schedule UI has been removed.
- **The `/cleaner/availability` calendar (`CalendarGrid.tsx`) is fixed at a 7-column month grid — there's no column-count zoom control any more** (the old +/- buttons that toggled between 1–7 columns were removed as unused/confusing; `columns` state, the `columns < 7` per-day weekday label, and the `columns === 7` conditional around the day-of-week header row all went with it). The color-legend row now sits **below** the calendar grid rather than above it.
- **The day-detail panel (opened by tapping a date) puts "Add availability" first, above the existing slots list, not below it** — so adding a slot doesn't require scrolling past whatever's already booked/recurring/added for that day. The empty-state placeholder text ("No hours set yet. Add some below.") was dropped for non-past days now that the add form is right there at the top; a past day with nothing on it still shows `avail_no_hours_past`.
- **Adding a specific-date slot can carry an optional free-text note** (`cleaner_availability.note`, nullable `text`, migration `0022_availability_note.sql`) — a textarea between the time-range pickers and the Add button, for anything the cleaner wants to flag about that day (or in general) before a customer books. `addAvailability` (`(cleaner)/actions.ts`) reads it from the form and stores it (empty string → `null`). Currently only surfaced back to the cleaner themselves (shown under the slot in the same day-detail panel) — **not yet threaded into `/browse`, `CleanerCard`, or the booking form**, so a customer doesn't see it yet; that's a separate follow-up if wanted.
- Customer browse (`/browse`) and booking validation (`createBooking`) match against the **union** of per-date and weekly slots. **Browse matching is by an availability *range*, not a single start time** (see the Hours preferences & availability range section below): the customer drags a dual-thumb slider (06:00–22:00) to say when they're free, and a cleaner shows for a date when the **longest continuous overlap** between that range and any one of their slots is at least `max(cleaner.min_hours, chosen duration)`. With no range set, a cleaner shows if they have any slot that day. (The per-card availability badges still show each cleaner's full slots for the day.)
- **Browse uses the customer's *profile* address as the search location — there is no location field on `/browse`.** `page.tsx` reads the signed-in customer's saved `customers.address` + geocoded `customers.lat`/`lng` (set on `/profile` save) and uses those coords for the distance filter (geocoding the address only as a fallback when coords are missing). `hasLocation` means "the customer has a saved address"; `locationError` means that saved address couldn't be resolved. - **`createBooking` blocks duplicate requests: at most one *live* pending request per customer per cleaner per date.** Before inserting it checks for an existing `pending` booking (same `customer_id` + `cleaner_id` + `scheduled_date`) whose `response_deadline` is still in the future, and rejects with an error if found. - On approval, `respondToBooking` also cancels **all** of that customer's other still-`pending` requests (sets them to `cancelled`) — customers fan the same job out to several cleaners (and possibly other days), so accepting one clears the rest. Those siblings belong to other cleaners, so the cleaner's RLS-scoped session can't update them: this cleanup uses `createAdminClient()` (service role) to bypass RLS. - **`respondToBooking` deliberately calls NO `revalidatePath` at all.** On `/cleaner/requests`, `RequestCard` keeps the detail modal open after an **accept** so the cleaner can read the customer's phone number, and only refreshes the list when they close it (`handleClose` → `router.refresh()`). So the action does no revalidation; the client's `router.refresh()` on dismissal handles the requests list and invalidates the Router Cache (so `/cleaner/availability` re-fetches the carved slot on next nav), and the dashboard self-updates via its `RealtimeBookings` subscription. **Don't add `revalidatePath` back to `respondToBooking`** without re-solving the modal-closing problem.

  - **`num_people` and `num_kids_under_15` are no longer customer-editable.** Their inputs were removed from `ProfileForm.tsx`, and `updateCustomerProfile` deliberately **omits both from the upsert** (so existing values are preserved, not overwritten to null) — the old `kids ≤ people` validation (`profile.errKids`) went with them. The columns remain in the DB and the cleaner's `/cleaner/customers/[id]` household card still **displays** them when set. The `profile.peopleLivingHere` / `kidsUnder15` / `kidsHelp` / `errKids` strings are now unused but kept in case the fields return.

### Hours preferences & availability range

- **Hours-preference columns (migration `0013_hours_preferences.sql`, all nullable):** `cleaners.min_hours` / `cleaners.max_hours` (the cleaner's stated minimum/maximum job length) and `customers.max_hours` (most hours a customer will pay for — a **separate**, still-enforced concept, see below). Edited on the respective profile forms — the cleaner form (`(cleaner)/cleaner/profile/ProfileForm.tsx`) has a single "Minimum job length" input (there used to be a second, duplicate `name="min_hours"` field elsewhere on the same form — a real bug, since browsers only submit the first of two same-named fields, silently dropping whatever was typed into the second; removed) and a "Max hours per clean" input that can be left blank for no limit (`updateCleanerProfile` still rejects `min > max` as a data-sanity check when both are set); the customer form has a single "Max hours per clean" input. They're on the `Cleaner`/`Customer` types and `CleanerResult`.
- **Neither of the cleaner's own `min_hours`/`max_hours` gates anything — both are informational only.** Shown on the cleaner's profile (`CleanerProfile.tsx`, `ProfileView.tsx`, and the cleaner's own `ProfileForm.tsx`/`ProfileView.tsx`) purely so a customer knows the cleaner's stated standard (e.g. a student cleaner capping jobs at a few hours) without it mechanically blocking a request outside that range. This was a deliberate product decision, not an oversight — don't re-add cleaner min/max_hours enforcement without checking first. The **customer's** `max_hours` (their pay ceiling) is a completely separate field and is still enforced, in `editBooking` — a cleaner can't edit a booking to a duration longer than the customer's `max_hours` (read with the admin client since RLS hides the customer's `customers` row from the cleaner's session). `BookingRequestForm`/`createBooking`/browse's duration filters now only apply a flat 1–8h sanity ceiling, unrelated to any specific cleaner's or customer's stated preference.
- **The cleaner registration wizard (`register/cleaner/page.tsx`) asks for both.** The existing "minimum job length" question (`duration` key, default 3) is followed immediately by a new "maximum job length" question (`maxDuration` key, default 5, same numeric-input-with-"hrs" UI) plus a **"No limit" toggle button** next to it (`maxDurationNoLimit` state) that disables the input and saves `max_hours: null`. Both questions are in `DEFAULTED_KEYS` (optional/skippable — simply visiting the step counts as answered, so pressing Next without touching it keeps the default).
- **The browse search uses an availability *range*, replacing the old single start-time select.** `AvailabilityRange.tsx` is a controlled dual-thumb slider (06:00–22:00, 30-min steps, pointer-based so it works on touch + mouse) that writes hidden `from`/`to` time inputs. `page.tsx` parses `from`/`to`; for each `(cleaner, date)` it computes the **longest single continuous overlap** between the range and any one availability slot (a clean can't span a gap, so it's the best single block — not the summed total) and keeps the cleaner only when that overlap ≥ the chosen duration × 60 minutes (or > 0 with no duration chosen). No range → just "has a slot that day".
  - **The slider is a composite widget, so it's labelled as a group, not with a `<label>`.** It renders two `<button>` thumbs (each with its own `aria-label` "Availability start/end") + hidden `from`/`to` inputs — there's no single labelable field. `BrowseFilters` therefore uses a `<span id="availability-label">` (not `<label>`) and passes `labelledBy="availability-label"` to `AvailabilityRange`, whose root `<div>` gets `role="group"` + `aria-labelledby`. This is the correct ARIA pattern and avoids the "no label associated with a form field" a11y warning — do the same (group + `aria-labelledby`) for any other multi-control widget rather than reaching for `<label>`.
- **A booking also carries the customer's broader availability window** (migration `0014_booking_avail_window.sql`: `bookings.avail_window_start` / `avail_window_end`, nullable `time`) — separate from `scheduled_start` + `duration_hours`. The point: a customer can order a 3-hour clean while signalling they're free for a wider window, so the cleaner can offer to extend. The booking form **shows this window read-only** ("When are you available?", `HH:MM–HH:MM`) carried over from the searched `from`/`to` (threaded through `BrowseResults` → `CleanerCard` → `ScheduleCleanModal`, and via the `from`/`to` query params on the "View Profile" link → `cleaners/[id]/page.tsx` → `CleanerProfile`, mirroring how `duration` is threaded); defaults to `06:00`/`22:00` when there was no search. It's no longer an editable `AvailabilityRange` slider — the customer doesn't re-pick it, and the form's derived `computeStart` uses this window to choose a concrete `scheduled_start`. `createBooking` stores it; the cleaner sees a blue **"Customer available HH:MM–HH:MM"** panel on the requests `RequestCard` detail and the dashboard `CleanDetailModal`.

### Ratings

- **Mutual numeric ratings (1–5, no text reviews).** After a booking is `completed`, the customer rates the cleaner and the cleaner rates the customer, from the existing detail modals (`(customer)/bookings/BookingDetailModal.tsx` and the dashboard `(cleaner)/cleaner/dashboard/CleanDetailModal.tsx`, shown only for `status === 'completed'`). Server actions: `rateCleaner` (customer actions) / `rateCustomer` (cleaner actions) — each validates the rater is the booking's own participant and the booking is completed, then **upserts** into the `ratings` table.
- **One editable rating per rater per *ratee* (not per booking).** The unique key is `(rater_id, ratee_id)`, so a customer who books the same cleaner repeatedly leaves a single rating they can change; re-rating from any of those bookings updates the same row (`onConflict: "rater_id,ratee_id"`). `booking_id` just records which booking the latest rating came from. (Migration `0011_ratings.sql` created the table; `0012_ratings_one_per_ratee.sql` swaps the constraint from the original per-booking `(booking_id, rater_id)` to per-ratee — idempotent, run both.)
- **Averages are denormalized onto `cleaners.rating_avg`/`rating_count` and `customers.rating_avg`/`rating_count`**, kept current by an `AFTER INSERT/UPDATE/DELETE` trigger (`on_rating_change` → `refresh_rating_aggregate`) so reads need no aggregation. Both trigger helpers are `SECURITY DEFINER` (the rater must update the *ratee's* aggregate row, which their RLS can't) with `EXECUTE` revoked from anon/authenticated/public, matching the 0010 security-lint hardening.
- **To know "have I already rated this person", pages fetch the rater's own `ratings` keyed by `ratee_id`** and attach `my_rating` to each booking (customer `bookings/page.tsx` by `cleaner_id`; cleaner `dashboard/page.tsx` by `customer_id`). RLS lets a rater read their own rating rows and a ratee read ratings about them.
- **Display:** shared, i18n-free `components/StarRating.tsx` (`StarRatingDisplay` = fractional-fill read-only; `StarRatingInput` = clickable 1–5). The cleaner's average shows on the browse `CleanerCard`, the `CleanerProfile` header (customer view + preview), and the admin cleaner list. The customer's average shows on `/cleaner/customers/[id]` (under the name) and the admin customer list. **On `CleanerProfile` the rating sits in the header (where the language badges used to be) and the language badges moved into the stats card** (`cleanerProfile.languages`) — a deliberate swap.

### Supabase client hierarchy

Three distinct clients — use the right one per context:

| File | Use when |
|---|---|
| `lib/supabase/server.ts` | Server Components, Server Actions, Route Handlers |
| `lib/supabase/client.ts` | Client Components (`"use client"`) |
| `lib/supabase/admin.ts` | Admin-only operations requiring service role (bypasses RLS) |

`createAdminClient()` uses `SUPABASE_SERVICE_ROLE_KEY` and must never be called from client-side code.

### Database migrations

`supabase/migrations/000N_*.sql`, applied via `supabase db push` (Supabase CLI, linked to the one shared project). **All git branches share the same Supabase project** — the remote's migration-history table is flat and doesn't know about branches, so two branches both starting their next migration at the same number will collide (`supabase migration repair --status reverted <N>` fixes the bookkeeping after the fact, but check `supabase migration list` for the real next-available number before naming a new file, don't just increment off what's in your local branch). Postgres enum columns (`cleaner_status`, `application_status`) can have values added (`ALTER TYPE ... ADD VALUE`) but not cleanly removed — old/retired values are left defined-but-unused rather than attempting a type recreation.

### Middleware & auth

`middleware.ts` (project root) runs at the edge on every non-static request. It:
1. Skips `supabase.auth.getUser()` entirely when no session cookie is present (avoids a network hang).
2. Redirects unauthenticated users to `/login`. **Public routes reachable without a session are `/login`, `/register`, `/register/*`, `/signed-out`, and `/auth/*`** (the OAuth callback must run while still logged out).
3. Redirects authenticated users away from `/login`/`/register` to `/{role}/dashboard`.
4. Enforces role — only `cleaner` role can access `/cleaner/*` routes.

Role is stored in the `profiles.role` column and read from Supabase (not the JWT) inside middleware.

- **Sign-out lands on a shared `/signed-out` screen, not `/login`.** The `signOut` action (`app/(auth)/actions.ts`) clears the session then `redirect("/signed-out")`; all three navs (admin/cleaner/customer) call that same action, so their existing "Are you sure?" confirm modals feed into one post-logout screen (`app/signed-out/page.tsx`, "Log in again" → `/login`). `/signed-out` is a top-level route (root `LanguageProvider` only, no nav) and is public in middleware. `signOutToRegister` (→ `/register`) is unchanged.

- **`POST /api/auth/signout` only honors a same-origin `redirectTo`.** It resolves the `redirectTo` query param against the request origin and redirects there **only if the resolved origin matches**, otherwise it falls back to `/login`. This guards against an open redirect — a bare `new URL(redirectTo, request.url)` would resolve absolute (`https://evil.com`) or protocol-relative (`//evil.com`) values to an off-site URL. Keep any new redirect that trusts user-supplied destinations behind the same same-origin check.

### Registration & the signup trigger

Registration is a **two-step client-side flow** (not the legacy `signUp` server action in `app/(auth)/actions.ts`, which is dead code): `register/page.tsx` stashes `{email, password}` in `localStorage` (`pending_signup`), then `register/customer/page.tsx` / `register/cleaner/page.tsx` call `supabase.auth.signUp(...)` and write the role-specific rows. This requires a session to exist **immediately after `signUp`**, which only holds when **email confirmation is disabled** in Supabase — the profile/customer/cleaner writes are RLS-scoped to `auth.uid()`. (See the empty `app/(auth)/auth/confirm/` dir — a leftover from an older confirm-email flow.)

- **`register/page.tsx` requires a confirm-password field and blocks on an already-registered email before either role flow starts.** The password/"Confirm password" pair is checked client-side (`password !== confirmPassword` → `auth.register.passwordMismatch`, no network call) in `handleSubmit`. The email check calls the `email_exists(check_email)` RPC (migration `0020_email_exists_check.sql`) both on the email field's `onBlur` (immediate inline feedback + a `/login` link, styled like the other field errors) and again in `handleSubmit` (defensive re-check — covers autofill or Enter-to-submit without a blur) — the Continue button is also `disabled` while `emailTaken` is true. `email_exists` is a `SECURITY DEFINER` function reading `auth.users` (RLS hides that table from the client) and is **deliberately granted `EXECUTE` to `anon`**, unlike every other SECURITY DEFINER helper in this codebase (0010/0011/0015), which revoke `anon`/`authenticated` — this one has to be callable from the logged-out register page. Both role wizards (`register/customer`, `register/cleaner`) still separately handle a `signUp` race (two tabs racing the same email) via `signUpErr`; this RPC is a pre-flight UX check, not the source of truth.

- **The cleaner wizard's "Are you sure you want to leave?" dialog signs the user out to `/login` on "Yes, continue later," not the dashboard.** `register/cleaner/page.tsx`'s `phase === "confirm"` screen has two buttons: **"No, keep going"** (`setPhase("flow")`, resumes exactly where they left off — unchanged) and **"Yes, continue later"** (`handleContinueLater`), which calls `saveAndFinish()` (creates the account + upserts whatever's been answered so far, same as a normal submit) and then, on success, calls the `signOutToLogin()` server action (`app/(auth)/actions.ts`, mirrors `signOutToRegister()`) instead of `router.push("/cleaner/dashboard")`. The account and partial profile already exist at that point, so the intent is "come back and log in to finish" rather than landing mid-registration in a signed-in dashboard. This is a deliberate exception to the app-wide "sign-out lands on `/signed-out`" convention (see the Middleware & auth section) — `signOutToLogin()` redirects straight to `/login`, since the "leave" flow is a registration exit, not a normal logout.

- **On a normal (non-"continue later") finish, the congrats screen sends the cleaner straight to `/cleaner/availability` — not the dashboard — with a one-time welcome speech bubble.** The `phase === "congrats"` button (`register/cleaner/page.tsx`) pushes to `/cleaner/availability?welcome=1` and reads `auth.registerCleaner.startBooking` ("Let's start booking"). `WelcomeBubble.tsx` (co-located with the availability page, `"use client"`) watches for `?welcome=1` via `useSearchParams()` (wrapped in `<Suspense>` in `page.tsx`, as Next requires for that hook) and shows a dismissible speech-bubble card — introducing "Cindy" (a named assistant persona, not tied to any account/character elsewhere in the app) and prompting the cleaner to mark their available days — with a tail pointing down at the calendar below it. Dismissing it calls `router.replace(pathname)` to strip the query param so it doesn't reappear on refresh or a later visit. The cleaner's first name for the `{name}` interpolation comes from a `profiles.full_name` fetch added to the page's existing `Promise.all`. This works even while the application is still `status = 'pending'` — nothing in `(cleaner)/layout.tsx` gates `/cleaner/*` routes on approval status (only role), so a cleaner can set up their schedule while waiting on admin review, matching the bubble's own copy ("Once your profile is approved, hosts can start finding you right away").

- **A DB trigger creates the role rows too — the client cooperates with it, it doesn't own creation.** `on_auth_user_created` (AFTER INSERT on `auth.users`) runs `handle_new_user()`, which reads `raw_user_meta_data` and inserts the **skeleton** rows: always `profiles`, then `customers` (role `customer`) or `cleaners` + `cleaner_applications` (role `cleaner`). It defaults to `customer` when no role metadata is passed, and every insert is idempotent (`on conflict (id) do nothing` / `not exists`). This trigger lives in `supabase/migrations/0004_handle_new_user.sql` (it predated migrations and was untracked until then — query the live DB with `select pg_get_functiondef('public.handle_new_user'::regproc);` to inspect it).
- **The client must therefore pass `options: { data: { role } }` to `signUp` and `upsert` (not `insert`) its detail rows.** Both register pages pass the role so the trigger branches correctly (without it, cleaner signups also got a stray `customers` row), and they `upsert` `profiles`/`customers`/`cleaners` so they *fill in* the trigger's skeleton rows instead of colliding on the PK (`customers_pkey` etc.). The cleaner page does **not** insert `cleaner_applications` — the trigger already creates it, and that table isn't keyed on `cleaner_id`, so a client insert would duplicate it.

- **Google sign-in (OAuth) + first-time onboarding.** The `/login` "Continue with Google" button calls `supabase.auth.signInWithOAuth({ provider: 'google', options: { redirectTo: <origin>/auth/callback } })`. `app/(auth)/auth/callback/route.ts` exchanges the `code` for a session, then routes by role. Because OAuth passes **no role metadata**, `handle_new_user` defaults a new Google user to a skeleton `customer` — so the callback sends **Google-only users who haven't onboarded** to `/onboarding` (a role-choice + name/phone page). `completeOnboarding` (in `(auth)/actions.ts`, uses the **admin client**) writes the profile, and for a **cleaner** choice deletes the stray `customers` row and creates `cleaners` + a pending `cleaner_applications`, then finishes.
  - **"Needs onboarding" is detected from auth metadata, not the DB:** a user whose `app_metadata.providers` is `['google']` (no `'email'`) and whose `user_metadata.onboarded !== true`. `completeOnboarding` sets `user_metadata.onboarded = true` via `admin.auth.admin.updateUserById`. **The check lives only in the callback — do NOT re-add a middleware "backstop" that redirects to `/onboarding`:** a just-set metadata flag isn't reliably visible on the very next `getUser()`, so that backstop caused a redirect loop ("stuck on Finish"). The onboarding page navigates with a full `window.location.href` load afterward. Email/password users are never affected (their `providers` includes `email`).
  - **Requires dashboard config** (not in the repo): Google provider enabled in Supabase Auth with the Google Cloud Client ID/Secret, Google's authorized redirect URI = `https://<ref>.supabase.co/auth/v1/callback`, and `<site>/auth/callback` added to Supabase Auth → Redirect URLs.

### Server Actions pattern

All mutations are Next.js Server Actions (`"use server"`) in `actions.ts` files co-located with their route group. They always:
- Call `supabase.auth.getUser()` to get the authenticated user (never trust client-passed IDs).
- Return `{ error: string }` on failure or `{ success: true }` on success.
- Call `revalidatePath(...)` after mutations so Server Components re-fetch.

### Realtime

Realtime is implemented via headless `"use client"` components that subscribe to Supabase Postgres changes and call `router.refresh()` to re-render Server Components. See `RealtimeBookings.tsx` for the pattern.

### Geocoding & location

Cleaners enter a free-text `address` (persisted in `cleaners.address`) plus a `service_radius_km`. On profile save (`(cleaner)/actions.ts`) the address is geocoded via OpenStreetMap Nominatim and stored as a PostGIS `POINT(lng lat)` in `cleaners.location`.

- **Shared geocoder** `lib/geocode.ts` is used by both cleaner save and customer browse. It biases results to Israel/Hebrew (`countrycodes=il&accept-language=he`, overridable via `GEOCODE_COUNTRY_CODES` / `GEOCODE_LANGUAGE` env vars) — without this, ambiguous place names resolved to the wrong country.
- **Distance filtering happens in-app, not in SQL.** Browse fetches each cleaner's `location` + `service_radius_km`, parses the PostGIS point with `lib/geo.ts` `parsePoint()` (handles EWKB hex / WKT / GeoJSON), and keeps a cleaner only when `distanceKm(customer, cleaner) <= service_radius_km` (haversine). The customer's coords come from their saved profile address (`customers.lat`/`lng`, see the browse bullet above); results are then grouped by date.
- **Re-geocoding existing rows:** `npm run regeocode` (`scripts/regeocode-cleaners.mjs`) backfills/refreshes `location` for cleaners that have an `address`, with rate-limiting and a `--dry-run` flag.

### Email notifications

`lib/resend.ts` exports typed functions for each notification event (booking accepted/declined, application approved/rejected, new booking request). These are called from Server Actions. Email failure is caught and swallowed — it must not block the primary mutation.

### Support / help widget

A floating "Need help? Contact us!" bubble (`components/HelpWidget.tsx`, a `"use client"` component) is rendered on **every cleaner and customer page** — mounted once in each of `(cleaner)/layout.tsx` and `(customer)/layout.tsx`. A signed-in user opens it, types a message, and sends; the message lands in the `support_messages` table and admins read/resolve it at **`/admin/support`**.

- **The widget spans both i18n systems, so it consumes neither.** It sits in both layouts (cleaner uses `context/LangContext`, customer uses `lib/i18n/LanguageContext`), so instead of calling either `useLang`/`useLanguage` it reads the current language off `document.documentElement.dir` (both systems keep that in sync, `rtl` ⇒ Hebrew) via a `MutationObserver` and picks its own EN/HE strings from a local `STRINGS` map.
- **Send path:** `lib/actions/support.ts` `sendSupportMessage(message)` — a `"use server"` action that resolves the user from the session (never trusts a client id), stamps their `role` onto the row, and inserts via the user's RLS-scoped client. `support_messages` RLS lets a user **insert only their own** row and read nothing; the admin inbox reads/updates with the service-role client (`createAdminClient`), same as the other admin surfaces.
- **Admin inbox** (`app/admin/support/page.tsx` + `SupportList.tsx`) has Open/Resolved tabs and a "Mark resolved" action (`resolveSupportMessage` in `app/admin/actions.ts`, `requireAdmin`-gated). The **Support** nav entry lives in `admin/Nav.tsx` (`adminNav.support`); page strings are under the `support.*` translation namespace.
- Migration `supabase/migrations/0016_support_messages.sql` creates the table (apply by hand — no CLI linked; confirm the next migration number with `supabase migration list` first, branches share one project).

### Types

All shared DB types live in `types/database.ts`. The key enums are `UserRole`, `BookingStatus`, `CleanerStatus`, `ApplicationStatus`, and `ServiceType`. Per-feature view models live under `lib/types/` (`booking.ts`, `cleaner.ts`, etc.).

- **`cleaners.status` valid values are only `pending | approved | rejected | suspended`** (the `cleaner_status` enum). `/browse` only shows cleaners with `status = 'approved'`, so any other value silently hides the cleaner from customers. If approved cleaners stop appearing in browse, check their status values first — that exact symptom traces back to bad status values, not a browse bug. **(The `chen-notes` admin work proposed renaming this enum to `new/active/in_training/inactive/blocked`; that migration was deliberately NOT merged — the app keeps the four canonical values, and the admin screens were adapted to them.)**
- **The `cleaner_status` enum was once polluted with stray values (resolved 2026-06-25).** An out-of-band DB change had `ALTER TYPE ... ADD VALUE`'d `active`/`new` onto the enum, and cleaner rows were relabeled to them — so genuinely-approved cleaners no longer matched the `'approved'` filter and vanished from browse. Fixed by: (1) normalizing the data (`active`→`approved`, `new`→`pending`), then (2) `supabase/migrations/0002_retighten_cleaner_status.sql`, which recreates the enum with only the four canonical values (Postgres can't drop enum values in place, so the type is renamed-aside/recreated/swapped inside a transaction). Writing an invalid status now errors at the DB. To audit the enum: `select enumlabel from pg_enum where enumtypid = 'cleaner_status'::regtype;`
- **Bulk status updates via PostgREST that filter on `status` and chain `.select()` hang against this DB** (e.g. `.update({status}).eq('status', x).select()`). Update per row by `id` instead when scripting status changes.
- **Migrations are applied by hand — there is no Supabase CLI linked** (no `supabase/config.toml`, no `db push` script). The files in `supabase/migrations/` are the tracked source of truth, but adding a file does **not** change the live DB; the user must run the SQL in the Supabase SQL Editor (or `psql`). When you add a migration, tell the user to run it, and remember the app will error on the new column until they do.
- **After adding a column, reload the PostgREST schema cache** or writes fail with *"Could not find the 'X' column of 'bookings' in the schema cache"* even though the column exists. Append `NOTIFY pgrst, 'reload schema';` to the migration SQL (or use Dashboard → Settings → API → Reload schema). This bit us on `cleaner_ack_cancelled` (the column was present; the cache was stale). If a brand-new column errors as "not found" but `select` shows it exists, it's the cache, not a missing column.
- **`0010_security_lints.sql` addresses the Supabase database-linter SECURITY warnings** — drops the broad public-read SELECT policies on the `avatars`/`gallery` storage buckets (public buckets still serve by URL via `getPublicUrl`, only the *list* API is removed) and revokes RPC `EXECUTE` from anon/authenticated/public on the SECURITY DEFINER functions `handle_new_user`, `rls_auto_enable`, and the `st_estimatedextent` overloads (they're triggers / unused, so this doesn't affect them). Two lints are intentionally left: **leaked-password protection** (Pro-plan-only, unavailable on free tier) and **`extension_in_public` for `postgis`** (moving an installed PostGIS extension is risky on managed Postgres and could break the `cleaners.location` geometry — not worth it; the `st_estimatedextent` revokes already remove its practical RPC exposure). New SECURITY DEFINER functions should likewise revoke `EXECUTE` to stay lint-clean.
- **Guard direct DB access.** The enum pollution above came from a manual/out-of-band write (Supabase SQL Editor, dashboard table edit, or an external script) — it left no trace in git or app code, so it can't be diagnosed from the repo. The app itself only ever writes the four canonical statuses (`handle_new_user` inserts `pending`; admin approval writes `approved`). Treat any non-canonical status, or any schema/enum change not represented by a file in `supabase/migrations/`, as an out-of-band change to investigate. Make schema changes via tracked migrations, not ad-hoc SQL Editor edits, and limit who holds service-role / direct-Postgres credentials.
- `ApplicationStatus` (`cleaner_applications.status`) is a **separate** enum from `CleanerStatus` — `pending | approved | rejected | needs_info` (the `needs_info` value comes from `0002_admin_panel_foundation.sql`). Approving an application sets `cleaner_applications.status = 'approved'` **and** `cleaners.status = 'approved'`; rejecting sets both to `rejected`; **"Needs info"** parks the application (`needs_info`) without touching the cleaner's status. See `app/admin/actions.ts` `updateApplicationStatus`.
- `cleaners.admin_notes` and `customers.admin_notes` (both nullable `text`, from `0002_admin_panel_foundation.sql`) hold free-text admin-only notes, persisted by the admin Applications screen.
- `admin_action_log` (admin_id, target_type, target_id, action, payload jsonb — also `0002_admin_panel_foundation.sql`) is a generic audit table for admin-triggered actions (reserved for later admin phases such as the Matching Queue's "notify cleaners").

### Internationalization (two separate systems)

The app has **two independent i18n setups** — don't mix them:

| Side | Import | Hook | Usage | Strings |
|---|---|---|---|---|
| Customer + auth + admin | `@/lib/i18n/LanguageContext` | `useLanguage()` | `t('namespace.key')`, `toggleLanguage()`, `messages.*` | `lib/i18n/translations.ts` |
| Cleaner | `@/context/LangContext` | `useLang()` | `t(translationKey)`, `setLang('en'\|'he')` | `lib/lang.ts` |

Both drive RTL the same way: `document.documentElement.dir = lang === 'he' ? 'rtl' : 'ltr'`. With `dir` set, Tailwind logical utilities (`text-start`, `end-0`, `justify-start`) flip automatically — prefer them over `left`/`right` so layouts work in both directions.

- The customer **profile page is fully translated** under the `profile` namespace in `translations.ts` (`ProfileForm.tsx` uses `useLanguage()`; the page title moved into the client form so it translates). A dead `profileForm` namespace + a stub `profile.title` were removed when this was wired — `profile` is now the single source. Server-action validation messages return **keys** (`profile.err*`) that the form translates, since a Server Action can't read the client-stored language.
- The customer/admin `t(key, vars?)` accepts an optional `vars` record for `{placeholder}` interpolation (e.g. `t('admin.dashboard.attentionApplications', { count: 3 })`), matching `{name}` tokens via simple `.replace()` — the admin dashboard's needs-attention strings rely on this.

### Environment variables

Required in `.env`:
- `NEXT_PUBLIC_SUPABASE_URL`
- `NEXT_PUBLIC_SUPABASE_ANON_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`
- `NEXT_PUBLIC_SITE_URL`
- `RESEND_API_KEY`

- **`next.config.js` derives the `next/image` allowed host from `NEXT_PUBLIC_SUPABASE_URL`** (parses its hostname into `images.remotePatterns`), so avatars/gallery load without a hard-coded host. A stale hard-coded host here previously blocked every Supabase image with *"hostname … is not configured under images"*. There must be **only one** Next config file — a redundant empty `next.config.mjs` was removed because, if picked up, it would wipe this image config and the WSL webpack-polling. Changing `next.config.js` requires a dev-server **restart** (not just hot reload). It also sets `experimental.serverActions.bodySizeLimit: '10mb'` (see the avatar note below).

- **Avatar uploads are normalized to JPEG on the client before upload (iPhone fix).** iPhones shoot **HEIC/HEIF**; the raw file uploads fine but `next/image`'s optimizer and non-Safari browsers can't decode it, so the avatar renders broken and the save *looks* like it failed. `lib/image/normalizeImage.ts` (`normalizeImageToJpeg`) decodes the picked image (iOS Safari decodes HEIC into a canvas), resizes to ≤1024px, re-encodes as JPEG, and — critically — **never throws** (returns the original file on any failure, so a save is never blocked). Both `ProfileForm`s (customer + cleaner) call it in their file `onChange`, then write the converted file back into the `<input>` via `DataTransfer` so the form submits the JPEG. This made `handleFileChange` **async**, so `ProfileForm.test` mocks the converter and awaits the preview. The 1MB Server Action body limit is also raised to 10MB in `next.config.js` (multi-MB phone photos otherwise silently exceed it).
